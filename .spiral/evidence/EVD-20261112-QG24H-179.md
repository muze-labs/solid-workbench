### Review correction: click/tap to edit

The maintainer finds the visual direction good but reports a blocked core task:
“Click to add text” does not respond. In an isolated Chrome session against the
actual dev server, the text iframe is ready and contenteditable, yet its computed
pointer-events is none. A native mouse click leaves focus on the iframe body,
selection null, and both visible/native text empty after input. This exposes a
coverage gap: earlier edit helpers called editor.focus directly.

An accidentally duplicated old-layout CSS block separated the presentation-only
ancestor selector from the iframe rule, making pointer suppression unconditional.
Remove that duplicate and restore the existing presentation-only selector. No
storage, data, provider or layout redesign is introduced.

The desktop reproduction now clicks through to the textbox, places the empty
caret at zero and saves “Actual click typing” into the native deck. The main
Presenter browser helper now uses a native phone tap or desktop mouse click,
waits for the resulting click and editor focus, then uses native keyboard/input.
It does not focus the editor through its API for ordinary text entry. Waiting
for the tap's click also prevents delayed touch selection from racing Ctrl+A.

`npm run check` passes 234 tests and both builds
(/tmp/presenter-click-check.log). The complete pointer-based Presenter scenario
passes (/tmp/presenter-click-browser.log), including phone empty-text entry,
desktop/offline editing, native composition/reload and editing after presentation.
The separate desktop reproduction passes (/tmp/presenter-click-probe-fixed.log).
Browser automation does not certify physical phone keyboards or manual AT.
