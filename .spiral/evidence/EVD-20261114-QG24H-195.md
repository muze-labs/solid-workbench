## Review investigation: authentication/startup navigation trap

The maintainer reports a second-slide failure with expired credentials that
persists after login and blocks returning to the first slide. No further product
change has been made in response yet. All earlier passing checks predate this
new report and do not establish this workflow's correctness.

Probe 1: a real HTTP 401 image response produces “Request failed (401)” but still
allows leaving the slide. This does not reproduce the reported trap and must
not be treated as its cause. Log: /tmp/presenter-auth-probe.log.

Probe 2: an independent wire-contract provider registers as restoring, then
reports restore-error “Sign in again to continue with Solid.” before becoming
ready or receiving a capability request. The host shows that error; selecting
the other slide leaves position unchanged and reports “Could not confirm safe
closure. capabilities: View connection is unavailable.” Restoring provider
availability, notifying the existing authentication-restored action and choosing
Retry still leaves the slide trapped. Text in the sibling editor is preserved.
Log: /tmp/presenter-auth-startup-probe.log; disposable script:
/tmp/presenter-auth-startup-probe.mjs. Both disposable probes intentionally stop
with “auth probe complete” after printing results; that exit is not a test pass.
The current served build was readable (cold fixture 1984095 B / 17 entries),
not the preceding minified cold fixture. No production-size inference is made.

Effective code explains this reproduced path: EmbeddedView.close negotiates
prepare for every attached provider, even when broker startup failed before a
content request was delivered. The broker refuses view operations for a provider
that never became ready. Retry tries the same closure first, causing the same
refusal. Attachment alone does not establish a content invocation or draft;
missing support alone is also insufficient to prove a started editor has no
recoverable work. Any correction must preserve guarded closure once a content
request may have reached a provider.

Presenter also has no onAuthenticationRestored hook; its onConnect handler returns
immediately for the same deck owner. This is code evidence, not a reproduction
of real OIDC token expiry/re-authentication. Exact user-facing message remains
requested so the real path can be distinguished from a plain denied read.

The evidenced gap and proposed behavior (safely leave/retry failed startup;
retain unsaved-work guards after content delivery) have been presented for
confirmation under the Spiral intent/reality gate. Existing CYC193 work is
preserved; no commit, integration or acceptance is inferred.
