# Preferences for independent apps

Status: Active, Evaluate (earlier planning chronology retained). The maintainer confirms the proposed goal with
“yes” on 2026-11-16. Execution boundary remains under design discussion.

Goal: an independent app can open common preferences and supply its own settings
section without rebuilding Preferences. Continue the high-priority library
boundary roadmap and its explicit any-app Preferences requirement. The proposed
selection-toolbar extraction was withdrawn after the maintainer identified
different use cases and uncertain simplification; it is not part of this cycle.
RSK240 remains deferred.

Baseline: main aaab09869d404c3e9ad534634d79f67d479817af.
Verified branch: spiral/CYC-20261116-QG24H-242-independent-preferences.
Integration target remains main, with exact prospective integration validation
and human acceptance required before integration. No commit, merge, push or
publication is requested. Preserve design/solid-workbench-maya-icons.zip.

Evidence: Preferences' request handler rejects unknown app identifiers even for
the selected owner and correct capability. Its sections component imports four
suite apps and its HTML/build feature composition bundles their panels. The
existing shared presentation does not supply independent contributions.
SRC243 records the confirmation; DES244 records the design alternatives and
the current code boundaries.

App boundary: Preferences owns common settings and section navigation. Each
contributing app owns its specific meaning and behavior. Do not replace app
behavior with a generic form schema or require adoption of the suite stack.
Offline/recovery: preserve local common drafts, profile-linked native RDF,
conditional writes and conflicts. Optional unavailable sections must not block
common settings; uncached provider code cannot be promised offline. Provider
draft ownership and close/retry behavior must be explicit in the chosen design.
Phone: retain list/details navigation and a usable section within the viewport.
Accessibility: labelled sections and controls, keyboard navigation, focus
restoration and unsaved-change feedback. Separate automated Chrome evidence
from manual AT and physical-device review.
Download: load only the selected contribution; measure the complete graph and
cold usable task including provider code. The 200000 gzip-byte target remains
advisory. Normal use must not fetch optional inspection sources.

Evaluation: demonstrate an existing suite app and an independently hosted app,
including no contribution, unavailable contribution, rejected owner/capability,
draft retention, reload/retry, conditional-save conflicts and shared preference
propagation. Run npm run check and npm run test:browser for implementation.
Review whether caller coordination and bundled app assumptions actually decrease.

Pause/replan if existing routing cannot uphold contribution authority or recovery,
or if the selected execution model requires unrelated protocol/format redesign.
No product implementation or test result is claimed at this planning checkpoint.


## Execution boundary confirmed

The maintainer selects “App-hosted embedded settings view (recommended)”.
Proceed with app-owned documents and draft/save/recovery lifecycles; Preferences
owns common settings and navigation. No in-process third-party code loading.
The existing local WorkspaceBroker (already used for standalone app tasks) can
own the section's scoped port directly inside Preferences. This avoids granting
general nested embed authority in the outer workspace broker. The outer broker
continues to guard Preferences closure; Preferences must prepare its owned view
and retain failed/unready drafts until retry or explicit discard. Section URLs
must be verified against the actual caller origin supplied by the broker, not
an input origin assertion. Existing configured-provider URL checks stay intact.
