## Goal and evidenced gap

Provide a Documents app for PDF reading and annotation, standalone and through
the existing Files embedded-view integration. Support page markers, paragraph
markers where structure supports them, and actual selected-text highlights.
Personal annotations are the default. Named groups each occupy a separate
native Turtle resource containing their annotations and bodies, ready for
independent sharing through future permission tooling.

Storage clarification: each PDF-and-group pair has its own annotation resource
in a separate annotations folder, independent of the source PDF's folder, Pod
or website. One named group may span PDFs through separate resources, never
one shared file containing multiple PDFs. An optional index links source PDF
URIs and group identities to their resources. Do not infer write authority on
the document's origin or construct annotation destinations beside the PDF.

The current Resource Viewer supports text and raster images and rejects PDFs
in apps/viewer/src/components/viewer.mjs. Files already integrates persistent
embedded resource viewers. There is no PDF or PDF annotation provider in the
current app composition. This finding and the proposed boundary were presented
before the maintainer confirmed the revised scope.

### HTML display and replaceable editing

Annotations with bodies provide HTML content for display. Render sanitized HTML
through the viewer's SimplyFlow presentation, without loading or depending on
Cobalt to read notes. Editor-native content is optional supplementary data;
it cannot replace the portable HTML representation.

Cobalt is the default annotation editor, replaceable through the existing
capabilities API and provider preferences. Reuse the proposed edit-note-body
contract and existing transport rather than introducing a separate registry.
The editor returns a proposed body edit, including current HTML, to the viewer;
the viewer retains ownership of anchors, group selection, drafts and conditional
publication. Merely opening or accepting an editor result does not grant Pod
write authority to the provider. Preserve original content on cancellation,
failure or unsupported native-format conversion; never silently flatten it.

Verify reading HTML notes with Cobalt unavailable, default Cobalt editing, and
replacement by a second compatible provider without changing viewer code.
Editor dependencies belong to the measured editing workflow, not the initial
reading graph. Preserve draft recovery across provider interruption.

## Guardrails and scope

Boundary: Documents owns reading and annotation; Files owns browsing. Reuse
the capability transport, Metro, native RDF/workspace helpers and Cobalt public
APIs where they meet the contract. Inspect margin-notes for reusable practices;
do not copy its HTML paragraph-ID assumptions into PDFs.

Reading scope: public/authenticated Pod resources and local files; navigation,
zoom, rotation, selection, search, outline and original download. Keep the
source PDF unchanged. Format-specific presentation and anchoring remain behind
a small app-owned boundary suitable for additional formats.

Offline/recovery: preserve annotation drafts locally through reload,
disconnection, expired credentials and rejected writes. Partition document,
account and group state. Distinguish local preservation from confirmed Pod
saves. Explicit offline reading requires shell, engine assets and complete
document bytes; partial loading must not imply offline availability. Failed
browser persistence is visible. Unknown save outcomes need reconciliation.

Phone: verify PDF reading, marker/text selection, annotation editing and group
selection on a narrow viewport before desktop expansion. Keep reading location
when opening and closing the annotation panel.

Accessibility: keyboard-operable page navigation, text selection or equivalent
marker-based annotation, named controls, focus restoration and readable note
lists. Do not claim paragraph detection for unstructured/scanned PDFs. Verify
PDF text/accessibility layers as well as the application chrome.

Downloads: measure the complete core app graph, PDF worker/fonts/assets, first
useful page and first note on a slow connection. The 200000-byte gzip JS target
is advisory, including required dependencies and auth callback. Lazy loading
does not conceal the cost of the actual task; size warnings never block dev.

## Continuous scrolling preference

The maintainer prefers scrolling between PDF pages with lazy loading; paged
EPUB-style navigation and optional two-page presentation were suggested as
alternatives. Implement the preferred continuous reader first, retaining the
outline and previous/next controls as scroll shortcuts. Separate paged/facing
layouts remain later options, not silently included in this correction.

Keep page placeholders and page controls in SimplyFlow. Each nearby page gets
an independent PDF.js canvas/text subtree; distant canvases are released,
except a page containing keyboard focus or a live text selection. Render only
a viewport-sized buffer, estimate unvisited page dimensions from page one and
learn their own dimensions as they approach. Native scroller supports touch,
wheel and keyboard. Outline stays left and open across page jumps. Update
current-page markers and annotation targeting from the visible page, while
selected-text annotations retain the page their selection belongs to.

PDF bytes still use the existing bounded Metro read; lazy loading here is
page rendering, not incremental HTTP ranges. Loaded-document offline behavior
and local/conditional annotation persistence are unchanged. Download budget
remains advisory and the same PDF.js dependency is reused. Verify repeated
outline navigation, native scroll/End back-and-forth, canvas eviction and
re-render, mixed page geometry, selection identity and existing persistence.

Checked PDF.js 6.5.438 installed APIs and official PDFPageProxy render/getViewport
and examples (https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html,
https://mozilla.github.io/pdf.js/examples/). Each page owns its render task and
canvas; cancellation never shares a canvas between concurrent page tasks.

## Inline anchors, visible notes, external sources and thumbnails

Maintainer review explicitly requests paragraph + controls at the paragraph,
visible-anchor-only annotation cards without page labels, explicit authors and
additional external files rendered distinctly, plus optional thumbnails if
performance is adequate. Current implementation exposes a paragraph dialog,
lists every note in the writing group, omits stored creator projection and
replaces the writing group when opening a remote file. These are the evidenced
gaps within the existing active reader cycle.

Keep Documents as the app boundary. SimplyFlow renders paragraph controls and
cards; native PDF geometry only supplies placement and visibility. Keyboard Tab
reaches each + button; hover/click reveals it and touch uses visible buttons.
Cards use the actually visible anchor bounds, not the renderer prefetch buffer.
External annotation files are cached alongside the writing group, labeled by
source/creator, and read-only in this presentation. Preserve unknown RDF and
existing creators, including multiple creator values; never assign legacy notes
to the current reader. New signed-in notes use the WebID; anonymous notes retain
a local pseudonymous author identifier. No permission management is introduced.

Optional thumbnails render only near the thumbnail pane viewport with one task
at a time, bounded canvas retention and page-number overlays. Native buttons
scroll the main reader, keeping sidebar scale independent. No extra dependency;
PDF engine remains the known advisory-size excess. Loaded/cached source data
works offline; fetching a new external file still needs access and connectivity.
Verify phone and keyboard paragraph insertion, visibility filtering, source and
author preservation/reload, and thumbnail canvas counts/navigation/performance.

Specification: W3C Web Annotation Data Model Recommendation 23 February 2017,
section 3.3.2 Agents (https://www.w3.org/TR/annotation-model/#agents): creator is
optional, may have multiple agents, and is recorded metadata, not authenticated
proof. Retain native Turtle and existing application PDF-anchor extensions.
