# Use shared runtime globals in replaceable Workbench functions

The maintainer confirms that app and shared Workbench module code should call
Metro, jaqt, oldm and Simply through globals so user replacements have the
same dependencies, and then asks to start the cycle after roadmap review.
This continues the moldability roadmap and the accepted CYC286 example.
Before this cycle, Workbench links library bindings through ES module imports,
and exposing app definitions does not make every helper replaceable.

The verified branch `spiral/CYC-20261119-QG24H-290-runtime-globals` starts
from `30c246a`.

Migrate calls across the suite, expose app-owned functions through existing
definitions or explicit APIs, and verify that running callers follow a
replacement and its removal. Start with Contacts search and a shared data
helper. Publish readable originals only through existing optional build
assets. If the installed composition API cannot support a required live
replacement, record the concrete gap for the separate SimplyFlow work.

App boundaries, storage, network authority and core interaction stay the same.
Preserve cached address-book search, active drafts, native RDF, reconnection
and existing authentication and conflict handling. Exercise the phone search
using native labeled inputs and keyboard interaction. Compare complete graph
sizes including the callback, plus cold phone startup and time to usable
search. Keep optional authoring sources out of startup requests and preserve
the selected Turtle backend. Manual assistive-technology evidence is distinct
from browser automation.

## Dependencies for editing existing functions

Source inspection of the installed runtime and current consumers points to
three ways to make dependencies available.

- **Workbench app and data APIs.** Expose stable, inspectable names for profile
  fields and edits, document and collection sessions, URL validation, and
  capability calls. For each editable function, identify the relevant
  dependencies and how callers resolve the active version. For example,
  Launcher exposes its group module through `this.api.launcherGroups`, but
  `setShortcutGroup` still calls `shortcutGroup` through a private module binding.
  Notebook and Presenter create long-lived document sessions. Changes to a
  constructor entry and changes to an existing instance's behavior need
  distinct evaluation. Module source URLs and package names alone leave these
  call paths unresolved.
- **Solid Workspace.** Frequent use of `local.indexedDB` for recovery, caches
  and drafts makes `local` a candidate for a consistently named scoped
  dependency. Collection adapters also use `workspace`, `resource`, `graph`,
  `solid` and `collection`. Expose these to features that create or change
  sources or synchronization policy. Preserve the existing account keys
  and use the app's document APIs for conditional Pod saves.
- **Feature-specific tools.** Cobalt rendering, validation, clipboard and
  link helpers matter for Notebook, Presenter, Viewer and Documents.
  Keep the corresponding editor and controller APIs available in those
  features. Presenter and Viewer transformers close over Cobalt imports,
  and Documents transformers close over DOMPurify. Installed SimplyFlow
  calls transformers with the binding object, so their dependency path
  needs separate verification from `this.api` on actions. Documents loads
  its PDF engine and note editor on demand. Their existing entry functions
  are the seams to expose for custom reader and editor behavior.

The DS contributes templates, classes and CSS properties through the design
datasets. Solid requests, provider invocations, URL handling and HTML
sanitization can continue through their existing Workbench entry points.
The IDE preview contract calls for isolated fixtures or substitutes for
session and storage dependencies. Each remaining candidate needs evidence
from a running caller before expanding its exposure.

## Confirmed Launcher and Presenter proofs

The maintainer adds both proofs to CYC290. Launcher will resolve its current
group reader when a move checks membership. Presenter will make Cobalt
rendering and fragment validation available to its thumbnail transformer in
the binding context. Use the installed SimplyFlow binding path and keep the
transforms on the current app instance.

The proofs preserve the existing Launcher and Presenter workflows, loaded
offline data, account ownership, drafts, and native RDF. Check the existing
phone move and editing interactions and verify that original behavior can
be restored in the same running apps. Optional authoring data stays off
startup. Use existing dependencies and compare the complete app graphs.

The maintainer asks to review SimplyFlow gaps and proposed changes before
undertaking upstream work and approves scoping the transformer gap
separately. The [SimplyFlow follow-up](../../design/simplyflow-lifecycle-composition-design.md#scoped-follow-up-for-named-transformers)
covers the owning app argument and live lookup for named transformers.
Workbench's Presenter proof uses a scoped bridge against the published
version.
