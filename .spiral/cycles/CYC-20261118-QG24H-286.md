# Bind list views directly to SimplyFlow models

The maintainer says “lets do that first, I'll fix simplyflow's issues later”
after confirming the data-grid example binds directly to a model view.
Use the installed API to remove mirrored rows and duplicated search state
where the list can render its model directly. Start with Contacts and the
shared example. Keep the existing source tracking and cleanup for models
that require it until SimplyFlow provides the lifecycle fix.

The app boundaries and native RDF stores stay the same. Contact search stays
local to the open address book, including cached contacts offline, and retains
its normal session restoration and separate recipient-picker search. Verify
filtering, refresh, restoration and native labeled search on phone and desktop.
Use existing runtime bindings and measure the build's app download report.

## Implementation

Contacts puts the model in app data and binds both list templates to
`peopleModel.view.current`. The model owns the address-book search and the
transient recipient search as separate options. The session captures the
address-book option and restores it through the existing publishing action.
An effect still supplies the empty message. The design example binds directly
too and omits the extra source effect because its fixture rows are fixed.

Presenter slides, Notebook blocks and documents, and profile details have
effects that only copy rows. Files, Documents and Launcher also mirror rows,
but their effects serve other purposes such as producing an empty message,
refreshing author profiles or coordinating shortcut screens. Preferences and
the collection browser transform their model results for presentation.
This first case gives those migrations a verified example. Component
adoption and the SimplyFlow model lifecycle change remain separate work.

## Evaluation

`npm run check` passed all 42 test files and the build. The Contacts refresh
test preserves sorting, the query and native RDF across source replacement.
The integrated Chrome scenario also exercised the Contacts template override
in an independently composed view and regular contact editing. The focused
design example passed its search, keyboard, phone layout and native component
checks. The phone recipient scenario tested a real text input in Contacts,
capture and restoration of the address-book search, and a matching recipient
in the capability iframe.

Contacts measured 129615 bytes gzipped for minified JavaScript including auth
callback, 19 bytes above CYC282. The focused cold phone picker with a cached
address book and warm caller transferred 554305 bytes over eight requests
and reached selection in about 11 seconds at 50 KiB/s down, 25 KiB/s up and
150 ms latency. These are browser measurements. No physical device or manual
screen-reader session was conducted.

The full browser command passed Contacts, the managed workflows, Preferences,
the recipient capability, Files, Presenter, Launcher catalog and demo styling.
It stopped in the Notebook native pointer assertion for the Bold control
(`test/notebook-browser.mjs:242`, called from line 1109).
Notebook passed its complete isolated rerun, including the pointer action.
The independent shared layout check passed for all ten apps. The full
browser command did not reach its later scenarios.
