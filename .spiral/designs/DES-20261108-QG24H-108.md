# Preferences app: proposed design for discussion

Status: Implementation authorized after design review: the maintainer says
“lets start”, following confirmation of immediate application and inactive
workspace editing. Goal/boundary/layout and immediate behavior are
confirmed; this document proposes their technical and interaction realization.

## Existing behavior and evidenced gap

At baseline main 0912f86b171b1296ada2514dfa70b9cd95f4801f, solid-app-ui
statically imports preferencesDialog, constructs it in each host,
and exposes its view. solid-preferences/dialog.mjs composes the full editor;
account.mjs opens the local instance. Its load/save flow both reads settings and
applies appearance. Workbench adds workspacePreferences/backgroundPreferences and
binds their runtime directly to the running Workbench app. Shared Save writes
through session.perform to the Pod; workspace/background controls have separate
explicit local actions and Save to Pod. This is not yet an independent editor,
immediate unified settings flow or inactive-workspace background editor.

The existing muzeSolidDesignListDetails component already supplies side-by-side
panes above 720px and horizontally snapping full-width panes below it, with a
Back command. Reuse that component and the-ds ds-panels structure. The existing
Back command focuses the first input/button/link rather than the selected
section; verify focus behavior in the embedded dialog and extend the existing
component only if the concrete workflow requires it. No new preferences layout
stylesheet or second renderer. The code inspection establishes composition;
embedded focus and download savings still require runtime evidence.

## UI and section contributions

One Preferences app serves its own route and embedded capability presentation.
Keep the shared Preferences menu item in its current position. Opening from an
app shows common sections first, then that app's sections; standalone use offers
an explicit app choice using the suite's known manifests. No full app store or
provider-registry implementation is implied.

Suggested common sections: Appearance (theme/text size/density), Language and
Opening applications. Workbench contributes Workspaces, Background, Storage and
Advanced; Files contributes Storage, Contacts contributes its current address
book location. These labels/groupings are proposals, not extra feature scope.
Workspaces includes explicit create/rename/delete actions and a workspace selector;
Background/Storage clearly show which workspace is being edited. Choosing a
workspace in Preferences changes the editor target only. The protected default/
active deletion rules remain. Diagnostics stays Workbench-owned, with an entry
under Advanced returning to/opening it through the host interface.

A section descriptor declares a stable app-prefixed ID, label, order, component
source and settings scope. Load its named SimplyFlow dataset in Preferences,
retaining editable templates/styles/actions/source origins. Keep the editor out
of the caller's startup graph. Reuse the suite manifest/build composition; first
support known suite contributions without inventing a general remote-code plugin
loader. Check existing APIs before finalizing descriptor encoding. The host owns
validation/domain changes; a section cannot bypass workspace protections.

## Immediate edits, local durability and synchronization

Proposed interaction: selecting a choice applies it immediately. Text fields keep
incomplete text as a locally retained draft and apply a valid value on completion
(change/blur or Enter); no save button and no Pod write for each keystroke.
Uploads validate/decode/cache before updating the workspace reference. Invalid
URLs retain their text and show field feedback, preserving the last effective
value. Create/delete remain explicit actions; typing a name never creates or
deletes a workspace. Explain saved-on-device/pending/synced/error states in plain
language; closing Preferences does not discard locally preserved work.

Separate preference reading/application from editing. Add a small host-side
consumer and use existing local native-Turtle document facilities for cached
common settings, pending changes and drafts, scoped by owner/resource. Inspect
Solid Workspace source/sync contracts before adding any missing narrow bridge.
Keep profile pim:preferencesFile and native workspace graphs authoritative;
preserve unknown statements and retain sufficient native RDF baseline for
conditional conflict detection. Do not serialize snapshots/baselines as JSON.

Serialize synchronization per resource and retain newer edits while an older
request is in flight. Coalesce pending valid changes, synchronize when connected,
and report Pod acknowledgement only after confirmation. Authentication failure
keeps local edits and offers existing reconnect/retry. A conflicting edited field
requires review; preserve unrelated remote fields and both choices. No silent
last-writer-wins. Initial offline use can offer defaults/new local choices, but
must not claim uncached Pod settings or overwrites are safely available.

## Host capabilities and workspace ownership

Use the existing capability invocation/private channel pattern. Opening conveys
the selected identity and app/workspace context; credentials stay with existing
authenticated clients. Workbench remains the sole writer of its live workspace
snapshot. Preferences sends narrow owner-bound operations with an explicit target
workspace ID and expected revision, not a replacement snapshot. Apply operations
against current state so an older editor cannot overwrite a concurrent switch
or directory change. No active-workspace mutation when editing an inactive one.
Deleting the target while it is open must retain the draft and report the missing
target rather than redirecting edits elsewhere.

Standalone common/app settings can use existing authenticated data APIs. If no
Workbench host is available, opening workspace editing should explicitly offer
opening/reconnecting Workbench; do not add an independent workspace writer.
Common settings changes notify open same-origin suite consumers to refresh their
owner-scoped effective settings without reloading app data or losing drafts.
Use existing managed/capability channels for embedded contexts where available.
On startup/reconnect/visibility recovery, refresh from retained local state and
then conditional remote state so missed notifications cannot become permanent.
Inspect existing library notification support before selecting a transport.

vertical path (common theme plus Files section), then Workbench's selected-workspace

markup from hosts only after replacement behavior works. Preserve existing

Measure complete production/readable app graphs plus callback, cold home task
and cold Preferences first-open with images/CSS/requests. Report actual savings;
keep the temporary Workbench cap unchanged and the new app below 200000 gzip

plugins, ACL editing and publication are outside this cycle.


## Keyboard section navigation, 2026-11-08

The maintainer requests Up/Down behavior like the dropdown, Enter to switch
sections and Tab into section controls. Inspection finds ordinary buttons with
no arrow navigation; activation currently moves focus to the heading. Extend
the existing list-details component with an opt-in section shortcut scope.
Arrows move focus and wrap without selecting; native Enter selects while
keeping keyboard focus in the list, and Tab moves to the displayed section's
first enabled visible control. Shift-Tab returns to the selected section.
Pointer activation retains heading focus and phone detail navigation. Native
arrows within input/select controls are unaffected. SimplyFlow binds a single
roving Tab stop, and stable row objects retain focused DOM nodes on activation.
No new CSS component or persistence change. This is an authorized correction
inside Active CYC106; human acceptance and commit/integration remain pending.


## Initial presentation focus and shared icons, 2026-11-08

The maintainer explicitly adds workspace-menu icon alignment to this cycle and
reports arrows unavailable, suspecting stale server assets. Installed the-ds
sets ds-icon vertical-align to bottom; CSS center is invalid. Apply middle to
the suite's shared svg.ds-icon default in its existing foundation style, without
editing node_modules or the external design-system repository.

Live HTTP checks on port 4174 confirm the actual process serves this checkout's
current bytes with Cache-Control: no-store. A fresh Chrome probe against that
server reproduces outer Close-button focus and child BODY focus; Down works only
after manually focusing the section. The cause is presentation focus, not stale
served bytes. Preferences now receives an initial focus request after SimplyFlow
has removed iframe inert/hidden/busy attributes. A native MutationObserver waits
for that concrete browser state; it does not render content. An immediate check
also handles an already-interactive frame. The callback targets current actions
and respects an interaction already started by the user.

Only Preferences requests this focus policy. ManagedApp validates the parent
window, origin, live task/peer and exact ticket ID/key before invoking its optional
onFocus callback. Other capability providers retain their own focus behavior.
Observer cleanup and existing private capability lifecycle remain intact. A live
server probe verifies initial focus in the iframe's selected button and the
first Down reaching Language without setup focus. Human acceptance, commits and
integration remain pending.
