# Scoped child Escape and existing close guards

Use a named SimplyFlow window keydown event/action in the existing shared
capability-dialog component. No content DOM renderer or new event system.
For an unconsumed, nonrepeating Escape outside composition, let any local native
modal or open popover handle the key first. Otherwise an embedded ready ManagedApp
requests presentation close using its existing parent, exact origin and current
id/key. Ordinary managed windows and separate task tabs send no modal-close
request. Account retains its private-port close route with the same key policy.

The host checks window source, exact origin, active invocation id/key, attached
state and visible iframe modal, then invokes the same guarded action as Close.
Never directly close or synthesize a key on the parent. Repeated/reloaded tasks
must reject stale tickets; existing navigation recovery remains in force.
Existing save/dirty/disconnected guards and native focus restoration remain.

Installed SimplyFlow event declarations support window keydown with lifecycle
cleanup. ManagedApp already has scoped presentation-ready/focus messages; extend
that small presentation protocol rather than add broker forwarding machinery.
Independent cross-origin providers may implement the documented message directly.

Specification review, HTML Living Standard, 2026-11-12:
https://html.spec.whatwg.org/multipage/interaction.html#close-requests
https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element
https://html.spec.whatwg.org/multipage/web-messaging.html#authors
Escape close requests occur on keydown; cancelling that event prevents native
close processing. Each Window has its own close watcher manager. Leave native
inner close requests untouched; validate both message origin and payload. Do
not add CloseWatcher, whose activation/grouping semantics and browser coverage
would introduce a new lifecycle. Native cancel is still the owning dialog path.

Tests: real Preferences native Escape, native inner popup/dialog and consumed
key, Account nesting, Profile save/dirty guards, Files/Contacts cancellation,
independent cross-origin provider and stale/wrong-source requests, reopen and
reload. Run npm run check and all browser suites. Preserve manual AT and
cross-browser limits explicitly.


Focus evidence refinement: native Files Escape closes correctly, but Launcher's
picker control is disabled until the invocation promise resolves, which occurs
after native dialog closure. The browser therefore cannot restore focus to it.
Retain the existing selection guard and use aria-disabled while pending so the
invoker stays focusable; the modal still makes it inert while the task is open.
This is part of the confirmed focus-return requirement, not new picker behavior.
The keydown fixtures must open the actual diagnostics/details controls first.


Accessibility reference for the invoker refinement: WAI-ARIA 1.2 Recommendation
(2023-06-06), https://www.w3.org/TR/wai-aria-1.2/#aria-disabled, reviewed during
evaluation. aria-disabled communicates inoperability on a button; scripting
must enforce it. The existing selection guard supplies that behavior, while
native modality prevents interaction with the caller during the task. Focus
is preserved without changing the selected resource or adding focus timers.
