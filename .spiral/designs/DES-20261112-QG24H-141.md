# Proposed current-book recipient picker

## Understanding and evidenced gap

Enable explicit recipient selection via the provisional
https://vocab.muze.nl/capabilities/select-recipient operation, returning one
HTTP(S) @id identifying a contact or WebID. Do not infer identity equivalence,
authentication, mailbox delivery or permission from that URI. Use the native
contact identity; close/result paths preserve unselected caller data.

Contacts currently opens an account/resource-scoped local collection, filters
it through a SimplyFlow model and renders profiles inline. Its manage call
registers getState/restoreState only; ManagedApp defaults capabilities to []
and rejects unsupported operations. The Contacts manifest also has no capability
declaration. Launcher embeds Files/Profile/Preferences and resolves preferred
providers only for browse. The native preference binding currently filters on
browse. Generic transport exists but does not indirectly supply Contacts
selection or preferences/routing for it. EVD142 retains inspected locations.

Proposed first slice: add an editable Contacts selection component that reuses
its list model and existing book/cache. Give explicit select/cancel controls,
visible identity/source and selected-provider feedback. Keep a pending request
separate from normal Contacts editing and reject overlapping requests rather
than replacing a draft. Reuse managed cancellation/readiness/focus APIs and
clear invocation state on cancel/identity/context change. Restrict any exposed
data to the explicitly chosen identifier and defined display hints.

Extend the existing native provider binding and Default apps projection only
as needed for select-recipient, preserving browse/unknown RDF and whole-choice
conflicts. Use normal validated broker routing and exact invocation scope. Do
not broaden all app grants. Separately hosted caller/provider fixtures exercise
the real picker; independently implemented protocol peers must supply additional
replaceability evidence. Do not claim new permission sharing from the picker.

The proposed boundary uses the current configured book. Multi-book discovery,
creation and cross-workspace browsing/search remain roadmap requirements for a
subsequent slice unless the maintainer includes them now. This choice is pending
confirmation; product changes are gated on that answer.

## Guardrails and evidence

Boundary: recipient selection belongs in Contacts, exposed through a capability.
Offline/recovery: only cached rows, honest availability, no automatic draft
publication or address-book writes merely to select; preserve edits and unknown
RDF. Phone/accessibility: search and explicit native select/cancel work without
pointer gestures; focus returns to the caller. Download: no speculative new
runtime dependency; measure complete graphs, with advisory warnings. Keep HTML
and content rendering in SimplyFlow and HTTP in Metro/data APIs. Inspect current
public library APIs before designing missing bridges.

The project adopts Muze engineering/architecture preferences, library stewardship
for any shared developer tooling, and WPF-HUMAN-001. The material concern here is
authority/evidence: selection is not an access grant, and same-library fixtures
are not independent interoperability evidence. Keep these distinctions in tests
and evaluation. No new public standard implementation is selected by the
experimental operation URI; recheck relevant published specs if affected RDF,
auth or transport behavior changes.


## Scope confirmed, 2026-11-12

The maintainer chooses “Current book first (recommended)”. The concrete
Understanding/gap and first-book boundary are confirmed; implementation may
proceed on verified spiral/CYC-20261112-QG24H-139-contacts-picker.
Existing locally created contacts have urn:uuid identities. Preserve those as
contact identifiers alongside HTTP(S) identities; do not invent a WebID or
rewrite native RDF to fit browse URL validation. The recipient contract must
validate these explicitly and display the identifier without implying login.


## Implemented design refinement

The current-book picker is a separate read-only view in Contacts' existing app,
composed after its ordinary list/details view. Both use the existing list model;
selection mode never calls profile editing. The proposed result validator also
accepts the existing urn:uuid contact identities and validates HTTP(S) identities
without normalizing them. The shared provider editor selects a task before its
existing chooser/custom/reset fields, retaining per-task drafts and distinct
native choice/cache nodes. Existing embedded provider ordering is preserved.
The generic broker and scoped presenter require no production changes.


## Result usability gap — revised design pending confirmation

Human review demonstrates that a UUID-only result is insufficient for an
external app. Preserve the native @id, but distinguish identity, source location
and selected data. A source URL can help an authorized caller fetch a published
book and locate the UUID subject; it does not cover local-only data, pending
edits or an unauthorized caller. Do not fabricate a subject fragment URL or
change identities to pretend the subject is separately dereferenceable.

Propose a bounded, explicitly reviewed RDF description of the selected contact
in the response, plus source-document location when genuinely available.
Reuse OLDM/Turtle for native values and structured nodes rather than flattening
through the editable profile projection or exporting the whole shared graph.
Keep current versus remotely confirmed data distinct, preserve the 64 KB wire
bound, and fail honestly rather than silently truncating unsupported content.
This revises the prior no-profile-data response boundary. Agree the selected
field/disclosure contract before implementation; no product code is changed
in response to this review yet.


## Concrete caller and useful recipient result authorized

The maintainer requests Files Share → choose someone, with no permission-change
flow, and explains that the caller is another app in the same Workbench/user
context. They explicitly choose “Include selected contact data when needed”
for local/unsynchronized contacts. They also request focused picker UIs distinct
from normal apps, reusing only useful shared controls/data APIs. This confirms
the missing caller and result-usability gap and keeps the correction in CYC139.

The revised result retains @id, an optional containing document locator, and a
bounded native Turtle selected-subject description. The built-in picker works
from a local graph, so it supplies that current description as a fallback rather
than asserting all rows/edits are already published. A document locator alone is
read by the caller's own Metro session; no credentials are passed. The picker
previews the exact returned RDF. It includes the chosen subject and anonymous
values, not other named contacts. Shared/cyclic anonymous values are explicitly
refused by this bridge because the installed object-graph writer would flatten
or recurse; there is no silent data loss or full-book export.

Files gets a per-resource Share action and a selection-only summary showing
name, email/phone/public-profile hints and original identity/location. It writes
no ACL or invitation. Cancellation preserves the previous selection. Native
workspace state retains only resource/entity/document references and a label;
contact RDF is never embedded as a serialized snapshot in Turtle state.
Local-only chosen data works without publishing the book. Files' resource picker
gets a task-focused list instead of the normal management table, with existing
folder navigation and native Select/Cancel. No edit/upload/share controls appear
in picker mode. Phone, keyboard, focus, source/draft preservation and complete
download graphs remain the evaluation conditions; prior passes are historical.
