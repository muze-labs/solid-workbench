# Reuse collections around Presenter's deck workflow

Extract Notebook's category/entry browser HTML, CSS and model projection into a
prefixed SimplyFlow component in existing shared UI. Both apps bind the same
fields, native links, category navigation and models; app-owned configuration
supplies labels, route links and selection/create actions. Keep app management
and document policy in their app components; do not copy Notebook's 1175-line
workflow wholesale into Presenter or create a generic lifecycle framework.

Presenter uses native collection/default/lifecycle APIs directly. Default subject:
urn:muze:solid-app:presenter in the profile-linked preferences file. The collection
format remains version 1; deck entry kind is muze.presenter. Defaults use the
first profile-advertised storage only when genuinely absent; prepare a native
pending default, conditionally create/sync it, then publish only if still absent.
Defined unavailable defaults retain their reference and any local listing.

The route uses encoded resource=collection and document=member, category and
create=deck. A direct Deck resource opens independently, never silently imports.
Collection switching does not make default. The current local deck remains in
its existing owner-scoped store; a native local-target reserves a managed new
file until explicit save. Loaded current drafts can reopen offline; other deck
bodies need access. Preserve dirty deck/open guards and close/prepare embedded
views before changing editor context. A toolbar Current deck action can resume
retained work without adding an extra overview entry.

Management uses labelled native dialogs with top-right close and immediate local
metadata edits. Native list/details/categories and shared controls follow the
existing visual language. Use model options for transformations. New managed
members can be physically deleted only through confirmed ResourceLifecycle;
linked removal leaves content. Moves/deletion preserve retry journals and repair
collection/current-deck references before acknowledging completed operations.
Files retains its separate tombstone-only command. Unknown/native RDF stays
through existing StateGraph/projection bridges and conditional helper writes.

Expose shared browser/config/actions and optional source entries for moldability;
normal use does not fetch authoring assets. Keep source and chunk ownership
explicit. Muze culture favors direct reuse and visible policy; the human-impact
profile requires actual recovery/accessibility evidence and no authority implied
by collection membership. No publication or new dependency is needed.
New exact source/design bindings await authorized commits; predecessor constraints
and immediate lineages are retained in IMP226.

## Protocol boundary and lifecycle integration

Checked PDS Interop's Solid Link Metadata and Solid Storage Specification
(Living Document, 24 January 2022):
https://pdsinterop.org/solid-link-metadata/ and
https://pdsinterop.org/solid-link-metadata/solid-storage-specification/ .
Parent description discovery uses advertised metadata links, including inherited
metadata where applicable; a directory pathname alone does not establish
metadata authority. Existing ResourceLifecycle handles the explicit physical
file workflow with conditional validators and advertised metadata. This is an
app-supported PDS workflow, not a universal requirement that all Solid servers
implement this extension. Files continues its tombstone-only policy.

Checked Solid Protocol 0.11.0 (12 May 2024), auxiliary resources:
https://solidproject.org/TR/2024/protocol-20240512#auxiliary-resources .
Server-provided auxiliary links govern discovery; do not assume an auxiliary
resource can be written simply because the content resource can. Existing
failure/retry and metadata authority tests remain applicable. This cycle does
not alter these shared protocol implementations or generalize profile behavior.

## Accepted card-footer deletion correction

Each real Presenter card has a visible native footer button outside its open
link. New deck has none. Local and managed/Pod-backed decks use Delete; linked
members use Remove link. Confirmation names the deck, affected locations and
unsaved-change disposal; linked removal states that the source file remains.
Local reserved targets without a saved receipt do not authorize deleting an
unrelated file that may occupy that URL. Local deletion works without Pod access.

Reuse ResourceLifecycle for actual conditional Pod deletion and advertised PDS
metadata; keep its retry journal until local cleanup succeeds. Deletion now
purges matching owner-local copies, baselines and cached previews instead of
retaining a recovery draft. Closing the deleted current deck uses the existing
explicit discard path; unrelated current edits/views remain intact. Create an
unlisted empty current deck if necessary, and return focus to a surviving card.

Native local deletion markers prevent late queued writes/reloads from resurrecting
removed copies. Minimal pending cache-address records allow cleanup to resume
without keeping a deck snapshot. Preview generations and membership checks
reject late reads. Shared image assets are not deleted from Pods. No unsupported
physical DELETE is substituted for Files' tombstone-only policy. Notebook's
separate retained-draft policy is unchanged. Evaluate cancellation, local/offline
removal, Pod failure/retry, queued saves/previews, reload and keyboard/touch.
