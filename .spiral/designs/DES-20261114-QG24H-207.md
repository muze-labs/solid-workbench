# Portable collections in Notebook

CYC205 continues the confirmed collection roadmap on its verified branch. The
maintainer confirms managed creations, linked additions and explicit permanent
file deletion. Existing local notebook recovery remains available; no implicit
upload/import of old drafts or lifecycle adoption of picker-opened files.

## Data and library contracts

Version 1 uses an experimental monorepo-owned collections namespace
https://vocab.muze.nl/collections#, with standard rdf:type, dcterms:title,
dcterms:modified and lm:deleted. Each file contains one Collection root and
stable named Entry/Group records referring to it. Root fields are version, title
and creation destination; entries hold document URL, cached title/kind, managed
boolean and group references. Documents remain separate native files. Shared
references are never declared owned children. Deleted entries retain their native
statements; unknown predicates, types, subjects and structured data survive edits.
Format recognition validates interpreted fields rather than a graph datatype list.

Reuse Solid Workspace 0.2.1 for supported replica merge/save ordering and local
sources. Its public custom source callbacks bridge the existing conditional
loadDocument/saveDocument APIs, capturing remote validators and preserving 404
as unavailable when opening a defined default. A 412 is a conflict, regardless
of the library's current generic offline status label.

A concrete installed-API probe finds an unrelated cyclic blank node causes the
normal OLDM writer to overflow during replica serialization. Preserve complete
raw native graphs using existing StateGraph, and project only editable collection
fields into the library's replica merger. Custom source callbacks overlay those
fields onto the authoritative full graph for local/remote writes, retaining
unknown terms, foreign types and cycles. Do not add a second merge algorithm,
change the shared parser default or serialize unknown structures through the
failing writer. The disposable bridge probe demonstrates concurrent additions,
conditional conflict/retry and foreign-cycle preservation. Keep this integration
limited to the documented serialization/header/default-read gaps.

## Navigation and startup

An explicit resource opens the identified collection or existing notebook. A
collection remains the resource URI; an optional document parameter selects a
member, encoded through URLSearchParams so nested fragments remain intact.
Otherwise use the account's app default collection through pim:preferencesFile.
Failed default reads preserve the selected reference/cache and expose retry;
they must not create an empty replacement or silently overwrite the preference.

The maintainer subsequently directs a normal collection overview page at startup,
with title listings, and automatic creation when no default exists. For a connected
account with a successfully read, undefined preference, use its first advertised
storage folder, reserve a UUID collection URL in a native local pending-default
record, create with If-None-Match, then conditionally publish the app default.
Re-read preferences before automatic publication; a concurrent default wins.
Retry reuses the same intent instead of creating additional collections. An
unreadable defined default remains selected and uses cached data where available.
Missing profile storage/access is visible and offers explicit picker recovery.
Signed-out local recovery remains available on the overview.

Ordinary collection switching is separate from Make default. Collection and member
addresses use native browser history; back/forward restores their context. The
collection's parent folder is its initial creation destination; changing it affects
future New operations. Existing per-device drafts remain accessible until explicitly
saved/added. Opening and on-device recovery do not silently adopt file lifecycle.

Notebook owns the library/list-to-editor interaction and editable feature data.
SimplyFlow's list models own filtering/sorting/group projection. Prefer native
buttons, selects and dialogs with clear keyboard focus/return and a useful phone
workflow. The accepted rich editor, H1 boundary and in-place formatting remain.

## Physical lifecycle and resolution

Reuse the existing configured Metro client; no new fetch/auth/retry stack.
Permanent deletion is an explicitly confirmed file operation distinct from
membership-only removal. Linked additions default to membership removal.
A physical operation records minimal native owner-scoped intent, source/target
URIs, validators and completed steps before irreversible work. Use conditional
requests, deterministic retry destinations and metadata from advertised parent/
ancestor descriptions. Avoid deleting storage roots, containers or unsupported
structured subjects. Refuse a workflow whose safe target/version cannot be verified.

A marker-first deletion can hide retained bytes on metadata-aware servers, so a
404 after marking is not proof of physical removal. Copy/move verifies destination
content before conditional source cleanup; destructive requests reject redirects.
Metadata publication and content cleanup remain separately journalled outcomes;
partial failure remains visible and retryable. Preserve RDF identities/relative
reference meaning when relocating a native document. Never reuse old identifiers
for unrelated content or substitute lm:forget for permanent deletion.

Resolution preserves original/current identity, distinguishes temporary/permanent
forwarding, deleted/unavailable/ambiguous states, rejects untrusted assertions and
bounds traversal. Whole-file, binary and ancestor scenarios need explicit tests;
no arbitrary third-party or own-sidecar assertion becomes deletion authority.
The existing Files mark-deleted action retains its established nonphysical contract.

## Specification references checked before implementation

- PDS Interop Solid Storage Link Metadata, living document dated 2022-01-24,
  https://pdsinterop.org/solid-link-metadata/solid-storage-specification/:
  sections 3, 4.1-4.4, 5 and 6 cover parent descriptions, responses, revival and
  ancestor behavior. These server rules do not prove bytes were removed.
- PDS link-metadata overview trust/ambiguity sections,
  https://pdsinterop.org/solid-link-metadata/: intrinsic/delegated authority and
  multiple targets require explicit client policy, not blind following.
- Solid Protocol 0.11.0, published 2024-05-12,
  https://solidproject.org/TR/2024/protocol-20240512: sections 4.3/4.3.2 and
  5.3/5.4 distinguish auxiliary discovery/deletion, conditional updates and
  physical DELETE. Strong ETags are optional; unsupported protection is visible.

These sources apply to the supported profiles/operations, not a universal claim
that every Solid server interprets PDS metadata. Verify actual client behavior
and fixtures/target-server scope, including response loss, concurrent editing,
metadata failure and redirects, before making compatibility claims.

## Confirmed minimal collection interface

The maintainer narrows the overview to document anchors and one New notebook
anchor. Global Collection options belongs in the app toolbar. Collection title,
search, membership management and lifecycle operations live in shared dialogs,
with top-right close buttons and no dismissal-only Done controls. Metadata edits
apply immediately through the workspace's admitted local saves; navigation and
account leave wait for pending persistence. Explicit operations remain buttons.
Categories use the existing shared list–details layout: category anchors in the
list, matching documents in details; the toolbar returns to the list on phones.
Native links preserve collection/category context and support separate launches.

The 2026-11-15 review makes list–details unconditional: All notebooks is always
the first category and is selected when no explicit category is supplied. Remove
the separate collection heading; retain the selected category heading as a
labelled focus target in details. Open the overview at those details on phones;
the existing Collections toolbar action still returns to categories. Give the
single New notebook link a decorative shared plus icon, retaining its text name.
No new dependency, transport or persistence behavior is needed. Verify empty
and populated collections, category selection and keyboard/phone navigation.

Notebook baselines and pending creations belong to a recovery copy, not just a
URL. Another copy's successful reload/save cannot authorize overwriting newer
remote content. Move repair rebinds a copy's validator only after its old validator
or baseline proves that it matches the moved content; stale drafts remain dirty
and conflict rather than acquire a fresh validator for older text.

Review refinements retain Files-style shared list controls with Notebook subtle
focus states. Empty-space clicks below the final editor focus its end using the
existing Cobalt API; controls, collection overview, busy/composing states and
selection drags are excluded. This adds no app boundary, network dependency or
persistence change. Phone click/tap behavior uses the native compatibility click;
keyboard navigation remains available. Verify native pointer placement in Chrome;
physical mobile and assistive-technology review remain separate limitations.
