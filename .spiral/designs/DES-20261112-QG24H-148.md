## Change next, through separately confirmed implementation scopes

1. **Bound and settle independent-provider calls reliably.** RSK149/EVD147
   reproduce oversized/non-JSON frames crossing the raw PortConnection boundary
   and a timeout:null call remaining pending when the remote port closes.
   Proposed next implementation-cycle goal: a caller gets one bounded result or
   a clear recoverable failure after a peer disappears, retaining its previous
   choice/draft and never replaying an invocation. A second-review Chrome probe now reproduces actual Contacts iframe reload:
   the request remains pending, the new app has no request, and Close offers
   Discard after the close guard times out. Discard recovers. Start with this
   concrete interrupted-task recovery case; investigate additional disappearance
   combinations only as needed to establish the supported lifecycle contract.
   Existing parent/popup monitoring already handles some full-app close paths;
   do not replace it with a speculative generic heartbeat service.

   First establish whether a size limit is needed, what resource or failure it
   protects against, and which data/boundary it applies to. The existing 65536-
   byte serializable helper is an implementation choice without a documented
   justification for that exact value, not an adopted universal transport
   budget. Distinguish restoration state, capability arguments/results and
   document content. Measure legitimate payloads, envelope overhead and actual
   resource costs. If a limit is justified, choose and document its value and
   failure/recovery behavior from that evidence. Do not turn 64 KiB into a
   global frame limit merely because the helper already uses it. Review frame
   shape/type handling independently of the decision to impose a byte cap. Include raw independent-peer tests so a passing
   serializable helper cannot stand in for the transport contract. Define a
   supported lifecycle signal or bounded liveness mechanism only after the
   composed reproduction identifies the gap. Healthy interactive tasks must
   tolerate user deliberation, cancellation must remain available, duplicate/
   stale replies must not apply, and no silent provider change or Pod authority
   is permitted. Update all in-project callers and fixtures together; external compatibility is not required.

2. **Make route and failure contracts precise.** Clarify preferred transient
   pickers versus legacy live browse, startup/readiness versus interactive
   deadlines, and explicit local close versus detected remote loss. The generic
   live-route no-provider message currently names Files even for another
   capability, and some refusal errors use the default failed code. Record
   these as targeted feedback/error-contract work when the transport cycle is
   scoped; no global error hierarchy is justified. Documentation is corrected
   in this evaluation to avoid claiming an enforced raw-wire limit or guaranteed
   automatic disconnect detection.

3. **Verify the accessible dialog workflow.** Retain the explicitly requested
   iframe Escape repair, including dirty/save guards and focus return. Existing
   native keyboard/AX/200% fixture evidence does not establish manual AT or
   cross-browser usability. This remains a concrete product follow-up after a
   confirmed reproduction; it is not silently implemented in this assessment.

4. **Reduce cold-task cost using measured bottlenecks.** Contacts currently takes
   about 13 seconds in the documented warm-caller/cached-book/no-store slow-link
   fixture. Evaluate complete app/data/assets and meaningful selection time,
   preserving readability/native state. No arbitrary allowance increase, bundle
   trick, strict build gate or unmeasured rewrite follows from this observation.

These are proposed priorities, not authorization of the next implementation
cycle. Transport boundary reliability is the recommended first follow-up;
manual review may select a different ordering explicitly.

## Remove / simplify

Remove overbroad current documentation claims that all raw messages are bounded
or that all remote disconnects automatically reject a pending interactive call.
The maintainer confirms this is a greenfield project with no API consumers
outside the project. Recommend retiring the obsolete chooseFiles/live-browse
route rather than retaining it for backward compatibility. The current picker
button already uses the preferred transient presenter. Audit and remove its old
API exposure, route/grant controls and associated state wiring where they serve
only that route. Update in-project callers and fixtures together; keep tests of
useful observable behavior on the surviving path instead of retaining obsolete
code to satisfy old tests. No compatibility shim or external migration period
is needed. Preserve authoritative RDF and unrelated data under the standing
rules; lack of API consumers is not permission to discard user data.

The second capability reused the existing broker and presenter. Keep that useful
architecture and simplify it by removing obsolete paths while correcting the
remaining transport boundary. Implementation belongs in the next agreed cycle;
this evaluation records the revised recommendation.

## Second review, 2026-11-12

The maintainer requests a double-check. The architecture and defer decisions
remain reasonable for the two demonstrated selection workflows; they are scoped
judgments, not proof that broader proposals are unnecessary. Correct the earlier
legacy-route usage claim and avoid treating a helper's byte limit as an already
agreed global-frame policy. The later maintainer clarification below resolves the external-consumer question.
There is no standards requirement here to restrict all structured-clone values
solely because the low-level transport accepts them.

The additional shipped-presenter/Contacts reload reproduction strengthens the
recovery recommendation beyond the original raw-port test. Prioritize that
concrete failure with visible retry/cancel and draft preservation. The observation
window is bounded; it proves pending after reload, not an experimentally observed
infinite hang. Current explicit discard recovery works. General heartbeat/crash
detection is still a possible later design question, not a selected solution.

The two independent-peer fixtures implement clients/providers around the actual
Workbench broker. They do not establish replacement with an independently written
broker. Retain that qualification when interpreting Phase 3/4 replaceability.


## Maintainer correction: greenfield APIs, 2026-11-12

The maintainer states that nobody uses these APIs outside this project and
legacy API support is unnecessary. This supersedes the earlier provisional
retention rationale. Tests demonstrating old behavior do not establish a reason
to keep it. Recommend removal of obsolete live-browse APIs and related machinery,
with coordinated changes to actual in-project dependencies. Message-budget and
protocol decisions should serve current requirements, not hypothetical external
consumers. Recovery and message-boundary work remain justified independently of
backward compatibility; include simplification when scoping that next cycle.


## Size-limit decision added, 2026-11-12

The maintainer agrees to explicitly evaluate the need, protective purpose and
scope of a size limit before selecting a value. The existing 64 KiB constant
is not a requirement to preserve or extend. Its acceptance by historical code
and repetition in later designs do not supply a measured rationale. This is
planning direction; no limit is changed or removed in runtime code here.
