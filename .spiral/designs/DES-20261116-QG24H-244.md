# Independent Preferences: execution boundary proposal

Status: proposed, not an approved loading mechanism. Goal confirmed in SRC243.

Inspected at baseline aaab09869d404c3e9ad534634d79f67d479817af:

- apps/preferences/src/components/preferences.mjs: swb_receivePreferences
  validates capability, owner and a fixed suite app list before initialization.
- apps/preferences/src/components/sections.mjs: static imports, contributions
  map and panel visibility assume known apps; simply removing the request
  allowlist would leave an undefined contribution array.
- apps/preferences/src/features.mjs and index.html: app settings templates and
  behavior are bundled at build time. Files and Contacts settings templates
  invoke Preferences' swb_changeSetting and use its runtime data directly.
- packages/solid-app-data/src/embedded-view.mjs: accepts a capability parameter,
  routes through the existing broker, validates presentation readiness, and
  supports provider-owned prepare/freeze before closure. This is a candidate
  mechanism; nested Preferences routing still needs verification.
- packages/solid-preferences/src/consumer.mjs: existing preference state,
  synchronization and announcement APIs must remain the common-settings owner.

Recommended boundary: an app advertises section metadata and an app-hosted view.
Preferences renders the navigation and common settings; the selected optional
section runs in the app's own document/origin and owns its edits and saves.
Use existing scoped capability ports and embedded lifecycle, with SimplyFlow
rendering the host and suite provider. Independent providers need not adopt it.
Do not send credentials or import arbitrary contribution JavaScript into the
Preferences runtime. Same-origin suite frames are not an isolation guarantee.
Owner checks and capability authority remain necessary in each provider.

Material alternative: dynamically import app-owned SimplyFlow components into
Preferences. This gives direct composition and shared state access, but grants
the component the Preferences document's authority, constrains independent apps'
implementation, and needs a deliberate code trust/loading contract. Goal
confirmation alone does not decide between these boundaries.

For the recommended design, resolve before implementation: descriptor identity
and source authority; app URL versus display name; managed and standalone broker
composition; provider owner verification; account/workspace scope; draft-close
vetoes and retry; selected-section focus; existing Workbench panels and standalone
application choice. No promise of generic dynamic-module loading or schema-driven
forms. Unavailable provider code must leave common settings usable without
discarding provider-owned edits. No cold-offline provider guarantee.

Prove existing Files or Contacts settings plus an independent section. Preserve
other existing sections until their ownership is migrated through the same
contract; explicitly record any remaining static dependency rather than claiming
full inversion prematurely. Measure actual complete graph and cold task cost.

Muze engineering informs explicit ownership and an early useful vertical slice.
Library stewardship applies to any shared API changes. WPF-HUMAN-001's premature
closure and authority-drift lenses are material to the execution-boundary choice;
they do not independently forbid either design. The maintainer decision remains
pending. No product modifications or browser verification have occurred yet.

## Execution boundary confirmed

The maintainer selects “App-hosted embedded settings view (recommended)”.
Proceed with app-owned documents and draft/save/recovery lifecycles; Preferences
owns common settings and navigation. No in-process third-party code loading.
The existing local WorkspaceBroker (already used for standalone app tasks) can
own the section's scoped port directly inside Preferences. This avoids granting
general nested embed authority in the outer workspace broker. The outer broker
continues to guard Preferences closure; Preferences must prepare its owned view
and retain failed/unready drafts until retry or explicit discard. Section URLs
must be verified against the actual caller origin supplied by the broker, not
an input origin assertion. Existing configured-provider URL checks stay intact.
