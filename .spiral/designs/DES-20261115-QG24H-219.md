# A shared native document save owner

Use one narrow DocumentSession class in existing solid-app-data. NotebookDocuments
and DeckDocument specialize it; shared owner holds owner identity, edit revision,
ordered recovery writes and conditional save/acknowledgement algorithm. Keep
existing public app controller APIs, storage names/keys/native metadata and app
models. Apps supply content(), persist() and baseline storage; Notebook supplies
its per-copy pending-creation store and post-save alias/target cleanup.

Why this boundary: no-change retains duplicate asynchronous save state machines.
A separate wrapper object would need forwarding accessors or callbacks for the
same live revision/address/dirty fields. A small base class uses the existing
controller fields directly, keeps one authoritative state and makes inherited
responsibilities visible. Avoid a generic lifecycle framework or renderer.

Shared save validates account/address, preserves the local copy, snapshots graph
and revision, determines safe existing/creation state, reconciles a matching
Notebook creation intent, delegates HTTP to existing loadDocument/saveDocument,
retains the required native baseline, clears acknowledged intent, updates remote
binding/dirty state and persists acknowledgement. Never clear edits newer than
the snapshot. Failed prior local writes must not permanently poison the queue.

Keep Notebook's always-retained per-copy baseline and redirect:error; Presenter
retains URL/owner-scoped baselines only when validators are absent and its current
request policy. Keep app-specific collision/account/address feedback. Notebook
permits opening a separate recovery copy while retaining its draft; Presenter
refuses opening over a dirty deck. Those load/activation paths stay app-owned.
No new simultaneous-save/cross-tab guarantees or automatic retries are promised.

Native Turtle remains authoritative; plain recovery flags/addresses keep current
predicates and lexical forms. No JSON snapshots or change to RDF writer contracts.
Expose the shared callable in both app APIs with a matching optional authoring
source descriptor; ordinary startup must not request it. No dependency additions.
Muze engineering/stewardship favors readable direct composition; the adopted
human-impact warning profile requires evidence of actual preservation and avoids
calling code movement alone a simplification. See the cycle guardrails/evaluation.

Following the maintainer's acceptance and commit/merge/push instruction, this
design binds confirmed source 801f75aab75f66e2cecbade98f47d440644c26df.
Existing predecessor design constraints remain effective in IMP220.


HTTP specification check before adopting the shared path:
- RFC 9110 (June 2022), sections 13.1.1 and 13.1.2:
  https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1 and
  https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2. If-Match uses strong
  comparison; If-None-Match:* prevents creating over an existing representation.
  Keep the existing document helper's validator checks and conditional headers;
  a baseline comparison is not permission for an unconditional PUT.
- Solid Protocol 0.11.0, published 12 May 2024, writing-resources/Conditional
  Update: https://solidproject.org/TR/2024/protocol-20240512#writing-resources.
  The profile encourages conditional creation and allows server ETags; it does
  not guarantee every successful write supplies a usable validator. Retain native
  baselines and safe validator reacquisition without automatic overwrite/retry.
The transport implementation is unchanged. Tests exercise both creation/update,
weak/missing validators, HTTP failures, unknown native RDF and lost responses.
