# Lifecycle bindings through an experimental SimplyFlow package

Status: **Implemented for evaluation, 2026-11-08 (IMP97/EVD98).** Human acceptance
is pending. Initial proposal/discussion text below is retained with the later
confirmed extension; the package README documents the implemented API.
SRC93 retains the explicit instruction to discuss this design before implementing.
SRC95 records the maintainer's subsequent decision: keep the new events section,
but implement its support as a separate package injected into Workbench's
SimplyFlow composition. Do not integrate it into SimplyFlow core yet. Promotion
is a later decision after the package proves useful. This revises the initial
upstream-first proposal; the lifecycle/API details below remain for discussion.

## Outcome and effective behavior

A person changing a feature should find the event and handling action together
in its dataset. The extension should attach and release the binding; the app keeps
the meaning of the event. An existing binding must call the currently effective
action, and removing an action override restores the prior behavior in place.

Read-only evidence at main fd7a6e6b943c1d862110107bb0353ba91bd3d3c6:

| Owner | Current event wiring | Proposed first migration |
| --- | --- | --- |
| Workbench lifecycle | window beforeunload/pagehide, attached after asynchronous initialization | Both events, preserving activation timing and exitAttempted guard |
| Shared account lifecycle | window storage; hashchange only when acceptLaunch is true | Both events, retaining the startup condition |
| Capability dialog | window message; dialog cancel; iframe load | Inventory only; later inclusion requires agreement |
| Shared dialog/toast/recovery behaviors | Element cancel/focusin plus cleanup | Keep existing behavior lifecycle in the first migration |
| ManagedApp and WorkspaceBroker | Message transport and browser lifecycle; abort signals | Keep in transport/data layer; no protocol migration |

The first two owners already use invocation-time forwarders and remove their
listeners during cleanup. This is an ownership/readability gap, not a reproduced
failure of action replacement or duplicate delivery. Workbench attemptExit already
checks persistence/session and suppresses the second close attempt; keep that
policy in its action rather than deduplicate distinct events in the library.

Installed simplyflow-app 0.10.3 composes components, binds commands/routes and
runs DOM behaviors with returned cleanup functions. Its behavior manager starts
on matching nodes and stops on node removal/app destruction. The inspected app
options do not implement a general events section. An arbitrary option becoming
an app property does not make that option operational. Existing suite
exposeDefinition wraps destroy to call app cleanup before SimplyFlow destruction.
The extension needs to stop event delivery before that cleanup and preserve
underlying destruction even when cleanup throws.

## Recommended boundary

Create an experimental, private workspace package, provisionally
@muze-labs/simplyflow-events at packages/simplyflow-events. This is the
maintainer-selected package boundary within this repository, not an external
sibling dependency or a package publication. Existing SimplyFlow npm dependencies
remain unchanged. The package owns EventTarget registration, invocation-time
forwarding and disposal; components supply event types, targets and action names.
Authentication, persistence, message validation and UI policy stay in their
current owners.

Installed SimplyFlow's mergeComponents/mergeOptions recursively compose arbitrary
object sections and assign unknown options to the app instance. Therefore an
events map already reaches app.events through normal component/app precedence.
Reuse that effective map instead of copying its merge implementation. Its nested
merge behavior also applies to descriptors: changing only action retains other
fields. Verify this with the actual installed constructor; do not promise atomic
descriptor replacement or a deletion convention that SimplyFlow does not provide.

Proposed explicit injection:

```js
import { app } from '@muze-labs/simplyflow/app';
import { installEvents } from '@muze-labs/simplyflow-events';

const view = app(definition);
exposeDefinition(view, definition, sources);
installEvents(view);
await view.actions.initialize();
```

This consumes the composed app.events declarations without replacing the exported
SimplyFlow app factory, mutating globalThis.simply or patching dependency internals.
App construction/rendering remain SimplyFlow's responsibility. All relevant
suite instances install the same package before their existing explicit
initialization. Do not install it automatically on unrelated views with no need
for event bindings.

Keep app.events as the inspectable declaration map. Expose the lifecycle
controller separately as app.eventBindings, with start/stop/destroy methods.
Reject conflicting installation/controller names clearly; repeated installation
on the same live instance should return its existing controller. Bind no events
merely by installing the extension. A destroyed app cannot be reinstalled.
Names remain proposed API spelling, not settled implementation.

Add events to the suite's existing definition/source metadata sections. Retain
original component descriptors and predicates, and expose overrides just as for
other entries. The extension consumes effective declarations; it does not
implement an IDE personal-layer manager.

Illustrative component dataset, not a drop-in API:

```js
events: {
  swbWorkspaceBeforeUnload: {
    target: 'window',
    type: 'beforeunload',
    action: 'attemptExit'
  },
  swbWorkspacePageHide: {
    target: 'window',
    type: 'pagehide',
    action: 'attemptExit'
  }
}
```

Named maps follow normal component/app override composition. New reusable names
use the suite prefix. The initial target set needs only the app container's
owning window, avoiding an assumption that global window always owns the app.
For conditional hashchange registration, a predicate evaluated with app context
at activation reads runtime.acceptLaunch. No reactive subscription is needed:
the present setting is established before registration. A future live condition
change would need an explicit contract rather than accidental reevaluation.

Do not add selectors, delegated DOM event syntax, propagation rules, polling,
transport routing or a general event bus for this first slice. DOM behaviors
already give element setup/cleanup a suitable owner. A future extension can reuse
binding internals where a concrete need warrants it.

## Activation and teardown

Recommend explicit, idempotent library activation at the existing ready point,
with automatic disposal on app destruction. Illustrative calls are
app.eventBindings.start() and app.eventBindings.stop(); final public names
remain open.
Calling start is not app-owned listener registration: the library alone creates
and tracks listeners. Workbench activates where its listeners are currently
attached, after initialization; account activates at the end of its synchronous
setup. Avoid migrating all startup to a new lifecycle convention just for this.

- Constructing definitions does not attach early listeners.
- Repeated start does not attach duplicates. Stop is idempotent.
- Destroy prevents all future activation, including a late asynchronous startup
  continuation. Startup side effects beyond binding remain governed separately.
- Dispose bindings before teardown can trigger more lifecycle handling. Existing
  suite cleanup still disposes workspace, effects and preferences. Install the
  extension after exposeDefinition so its destroy wrapper stops events before
  invoking suite cleanup. Its wrapper disposes its own resources even if cleanup
  throws; repair the existing suite adapter with finally-based underlying
  destruction if necessary so SimplyFlow also releases its resources. Preserve
  the original failure and idempotence; do not introduce a general plugin hook
  registry just to order these two existing responsibilities.
- One owner cannot remove another owner's listeners. Do not deduplicate across
  app instances; both may intentionally listen to the same window event.
- Preserve the current bfcache/pageshow policy. This refactor must not invent a
  new resume policy or claim beforeunload/pagehide guarantees a completed save.

## Dispatch, failures and replacement

Each delivery resolves the action by name from the live app.actions table and
passes the original Event synchronously with SimplyFlow's app context/error
handling. Do not capture a bound action at activation. Preserve native event
cancellation timing; do not schedule delivery or await before preventDefault.
The action proxy currently owns thrown/rejected action handling; do not report
an async failure twice. Native EventTarget does not await action promises or use
a handler return value as a persistence acknowledgement.

Validate descriptors before attaching. If activation fails partway through,
release listeners attached by that activation, report the failure and leave
other app owners intact. A missing/non-callable action must report a clear
binding/action error rather than silently drop the event. Confirm how this
fits the existing action proxy instead of changing global error policy.

For the first slice declarations are composed at startup. Replacing/restoring
an action is live; replacing an events descriptor is not promised to rebind
live. The future IDE may expose that limitation. Do not claim complete IDE
readiness from this cycle, or mutate the component originals while applying
app-level overrides. Expose events metadata and authored source alongside the
existing definition sections if the new library section is selected.

## Alternatives and costs

| Alternative | Assessment |
| --- | --- |
| Keep current forwarders | Already correct for current-action calls; lowest cost, but leaves the agreed registration ownership gap |
| Use app-defined behaviors | Reuses real setup/cleanup support, but app code still implements registration; useful for existing DOM behaviors, insufficient alone for this goal |
| Separate SimplyFlow events extension | Selected boundary: explicit declarations, package-owned bindings and local evaluation without changing or releasing SimplyFlow |
| SimplyFlow core integration | Deferred by maintainer; reconsider after the extension proves its contract and value |
| Duplicated per-app listener managers | Reject: the experimental package provides one shared mechanism; app-specific policy remains in named actions |
| Migrate all DOM/protocol listeners now | Defer: couples distinct lifetimes and authority checks without evidence it is needed for the four initial events |

This introduces one definition section and a small activation/disposal contract;
reuse existing SimplyFlow composition/error conventions. The extension is
app-owned experimental infrastructure in this monorepo, explicitly authorized as
a design direction by the maintainer; it supersedes the earlier rejection of any
local generic mechanism. Keep it free of Workbench/account policy so later
promotion remains possible without designing that promotion now.

No core fork, external repository edit, new release or publication is required
for the experiment. Future promotion requires evidence from multiple real owners,
a stable lifecycle/composition contract, readable source/docs, adequate tests and
acceptable measured download cost. Separate promotion/release review decides
whether it belongs in SimplyFlow by default; success here does not authorize it.

Muze engineering culture shapes the bounded slice and separation of policy from
mechanism; library stewardship shapes the readable public API and download cost.
These preferences do not waive the project constraints or design discussion.

## Guardrails and evaluation

App boundaries, data authority and storage behavior stay the same. Existing
locally available content/drafts and recovery remain usable; no new network
request is required for event delivery and no offline cache is introduced.
Preserve phone navigation and native keyboard/dialog interaction. Browser checks
establish regression evidence; manual keyboard/focus review is still needed,
and no assistive-technology user study is inferred.

Library contract evidence should cover synchronous dispatch/cancellation, one
call per event after repeated activation, action replacement/restoration,
activation failure rollback, conditional registration, independent instances,
stop/destroy and start-after-destroy, plus synchronous and async failures.
Integration evidence should exercise account storage/hashchange and Workbench
close/checkpoint flows in existing instances, retaining drafts and unrelated RDF.
A real browser must confirm app destruction and late-start safety. Preserve the
known workspace timing concern rather than silently retrying it away.

Run npm run check and npm run test:browser after implementation, plus
the experimental package contract tests. Measure minified and readable complete
app graphs including auth callback, and cold transfer/requests/time to a real
core task. EVD90's readable Workbench is 197003 gzip bytes; this is measured
baseline headroom, not a prediction of the new API cost. No new font/image/data
requests are expected; verify that claim.

## Confirmed custom-source contract and implementation boundary

Following the target/subscription and naming discussion, the maintainer says
“Ok, lets try this design.” SRC96 retains that confirmation and supersedes
pending implementation statements above. The section remains events. Add:

- target: 'window' or a synchronous function called with the app as this,
  returning an EventTarget. The original Event, including CustomEvent.detail,
  reaches the current named action synchronously.
- subscribe(notify): synchronous function called with app context, which
  connects a library-specific source and returns a synchronous unsubscribe
  function. notify(...args) forwards those arguments to the current action.
  Exactly one source form per descriptor; type belongs to EventTarget sources.
- when(): optional synchronous activation predicate, called with app context.
  False skips registration until the next stop/start. Reject async predicates,
  targets and subscription setup rather than claiming asynchronous lifecycle.
- Subscription setup may notify synchronously. Activate each source's forwarding
  guard before calling subscribe; stopping/destroying during setup must dispose
  even a subsequently returned cleanup. Reentrant start is a no-op.
- Stop/failure/destroy disables forwarding before running all cleanups, including
  when one cleanup fails. Retained callbacks from unsubscribed library sources
  become inert. A later start cannot revive old callbacks.

No payload transformation, before/after interception, veto/return-value protocol,
reactive descriptor replacement or event bus. Library adapters remain editable
component functions; the package controls lifecycle and current-action delivery.
Metadata must retain full descriptor source, including target/when/subscribe,
without breaking existing function-source reconstruction checks.
