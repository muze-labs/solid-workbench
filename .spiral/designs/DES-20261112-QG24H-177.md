# Presenter composition design

Current reviewed design: one background-image/centered-text slide template,
thumbnail list–details, inline Cobalt Bold/Italic/Link with reusable Feather
floating/docked toolbars, and local fullscreen keyboard presentation. Text is
native RDF stored with the deck, with provider recovery and durable host
acknowledgement. The maintainer authorizes a pinned local Cobalt 0.1.1 build until
upstream release; composition guards protect unfinished input. Pointer suppression
applies only in presentation mode. Earlier alternatives below are retained design
history, superseded by the explicit review revisions.

## Initial design and subsequent revisions

Continue accepted shared EmbeddedView with several independently scoped regions
and passive-bounded display. Use two layouts inspired by the inspected local
SimplyPresent: title/text and title/image. Stable slide and region IRIs, typed
order, layout and resource/provider links are native RDF; unknown statements
remain authoritative and preserved. The maintainer confirms native RDF text within the deck, with provider-owned editing and Presenter-owned saving.

Existing read-only resource viewing remains available in Files. Provider support
must acknowledge requested interaction/geometry; unsupported content produces a
recoverable region failure. No failure implies permission to discard edits.
Native controls select/reorder slides and regions without requiring dragging.

Storage inspection: Solid Workspace supplies local indexedDB Turtle sources;
its documented remote replica API does not implement conditional HTTP writes.
Use the suite's loadDocument/saveDocument through session.perform/client for
conditional Pod publication, with a narrow Presenter policy for retained local
work and conflict feedback. Do not duplicate HTTP/auth/parser infrastructure.
App behavior belongs in editable SimplyFlow feature entries. Existing shell,
shared dialog/loading, model/effect and event APIs cover UI infrastructure.

Library/source checks: installed SimplyFlow 0.10.4, Solid Workspace 0.2.1 and
SimplySolid public documentation; SimplyPresent local revision
 a01a3af855ba1a3d9ebc4846eb0bea84fd9f8cf8. Published HTTP/Turtle behavior is delegated
to existing checked document/native graph helpers. Final contract and evidence
will be recorded as the proof resolves its remaining decisions.

Resolved ownership: the maintainer explicitly confirms native RDF text within
the deck. Resource Viewer supplies separate text view/create/edit capabilities;
its editor returns an identified draft and never writes the deck. Presenter
preserves provider bindings and owns local/Pod durability. Plain text keeps this
proof bounded; rich text and separate reusable text documents remain later work.

The adopted Muze engineering culture shapes the phone-first vertical workflow
and readable features. Library stewardship applies only to shared EmbeddedView,
provider preference mappings and build tooling. Existing experimental contracts
are extended narrowly; no general provider/renderer framework is added. The
existing human-context warning lens is satisfied by retaining the explicit text
ownership answer, goal and measured performance limits rather than treating tests
as acceptance.

Specification checks before the affected integration corrections: RDF 1.1 Turtle
§6.3 (https://www.w3.org/TR/turtle/#sec-iri-references) requires relative IRIs to
use the in-scope base/retrieval URL. A Pod-relative root and unknown resource term
are tested through local reload. RFC 9110 §§13.1.1–13.1.2
(https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1) distinguishes strong
If-Match validation from If-None-Match creation. Reuse the existing helper;
conditional creation, 412 preservation, concurrent edits and refreshed validation
after a 205/no-ETag response have observable tests. No HTTP/parser default changes
or requirement inferred from a different Solid/auth profile is introduced.

MVP limits: one current local deck per account; save before replacing it. Text
provider drafts are separately recoverable. Offline claims cover native local
data and already loaded views, not uncached provider bundles or image bytes.
Passive bounded views explicitly reject overflow; exact MIME ranking, rich
formatting, general layout negotiation and multi-tab edit coordination remain
resilience/follow-up work. The uncompressed no-store development fixture measures
actual cold usable content, not a loading shell; its substantial cost is retained
as evidence rather than hidden behind the minified entry size.


## Review correction: slide composition and editing

The initial title/text and title/image form-based UI was not accepted. The
maintainer's revised direction supersedes that UI proposal: one background-image
and centered transparent-text template; large initial text; thumbnail list–details;
canvas-first editing and full-screen keyboard presentation. The exact toolbar,
phone layout and editor/provider interaction remain under discussion. Suggested
16:9 proportions and a horizontal phone thumbnail strip are agent proposals,
not recorded maintainer decisions. Do not expand the existing form UI further.

Margin Notes at commit 48172a979702721d77a47cb1801357b8e8964136 supplies a
concrete precedent, inspected from its source and docs/COBALT_RDF.md. Cobalt keeps
plain text and annotation values; an app-owned bridge maps text to rdf:value and
formatting to an ordered RDF Collection with typed start/end/order and tag values.
It preserves unmapped predicates and detached member facts. Display uses Cobalt
render through a SimplyFlow transformer. Cobalt owns only the editing surface;
the application owns storage and surrounding UI. Its modal reads getValue on
explicit Save, so it does not itself establish inline autosave. Presenter should
reuse this separation and mapping approach rather than flatten formatting or
store serialized fragment JSON. Whether generated alternative HTML is useful for
Presenter remains open; Margin Notes' Web Annotation ownership is not copied as
slide policy. No specification-conformance claim is made from this inspection.

The local SimplyFlow packages/simplyedit source supplies toolbar inspiration:
selection-relative labeled controls, pressed states, expandable subtoolbars,
Ctrl+Space at a caret, Escape dismissal, and optional toolbar injection. Inspect
its exported toolbar and selection-anchor APIs before inventing equivalents.
Viewport-bottom collision, virtual keyboard, selection/focus return, iframe
clipping, instance-scoped anchors and theme integration need explicit evaluation.
A compact application toolbar versus contextual text/background tools is a
proposal for a shared Workbench pattern, not a finalized control inventory.

The authorized Cobalt prerequisite adds a bubbling cobalt:change notification
with a detached fragment after actual text/annotation changes, including API
edits. No storage dependency belongs in Cobalt. It is developed on the separate
Cobalt branch feature/rich-text-change-notification and is not yet published;
Workbench must consume a published npm version when integrated, never a sibling
link. No Presenter product changes accompany this design investigation.

## Revised implementation decision

The confirmed toolbar study now governs the Presenter revision described in
IMP178. Use the existing published Cobalt 0.1.0 editor's public reactive fragment
input, with detached view data and microtask observation of completed operations.
This avoids an unpublished/sibling dependency while preserving the separate
change-notification proposal. SimplyFlow's installed 0.10.4 export map does not
expose simply.edit's toolbar; use a narrow solid-design placement/control feature
inspired by that source rather than importing private source or its editor.

The app/provider split is unchanged: Presenter saves native deck RDF; the editor
owns interaction and a native recovery draft. Add owner-scoped read/acknowledge
operations to the existing private view port. The cross-window change event is
only a notification, checked against the current frame/origin/generation. Clear
recovery data only after an explicit durable-deck acknowledgement. Rendering
snapshots are detached from live Cobalt state to avoid observing partial ranges.

New slides use one image-background/text composition. Native 16:9 proportions
and a horizontal phone thumbnail strip are implementation choices within the
confirmed list–details requirement. Existing resource-view defaults remain
unchanged; bounded image views explicitly request cover and text requests contain.
Editable bounded text can scroll; passive text rejects overflow. Native fullscreen
is requested during user activation and handles rejection/exit; fallback fills
the current viewport. No fullscreen capability is assumed for every host.

Specification check: RDF 1.1 Turtle §2.8 Collections
(https://www.w3.org/TR/turtle/#collections) confirms first/rest ordering and nil
termination. Read/write tests exercise order, empty lists and cycle refusal;
cycle refusal is app validation, not a new Turtle syntax rule. Fullscreen Living
Standard §3 API (https://fullscreen.spec.whatwg.org/#api, 2026-10-19 revision)
requires transient activation and permits rejected requests; request before
asynchronous collection, await completion, and handle fullscreenchange. Browser
tests cover native fullscreen and viewport fallback separately. These checks do
not claim whole-protocol or cross-browser certification.

## Authorized Cobalt composition correction

After the concrete data-loss probe, the maintainer explicitly selects fixing
composition in Cobalt first. Extend the existing rich-text change-notification
branch, preserving its edits. During composition, let the browser maintain the
provisional text; at completion reconcile its text change through existing
Cobalt commands, preserving annotation ranges and emitting one settled change.
Expose active composition so a caller can refuse premature teardown. Cancellation,
empty deletion, Unicode, pending formatting, API replacement and destruction need
specific regression checks. Do not add composition/storage logic to Presenter.

References checked before implementation: Input Events Level 2 Working Draft
2026-10-15 §7 (https://www.w3.org/TR/input-events-2/#input-event-order-during-composition)
and UI Events Working Draft 2026-02-21 §3.6
(https://www.w3.org/TR/uievents/#events-compositionevents). Composition updates
are browser-owned/non-cancelable in Input Events; UI Events requires compositionend
after the control update and permits empty data for deletion or cancellation.
The drafts differ on update/beforeinput ordering. Do not depend on that ordering
or treat the final event's data alone as proof of cancellation. Verify actual
Chrome behavior and retain cross-browser/physical-keyboard review as distinct.
