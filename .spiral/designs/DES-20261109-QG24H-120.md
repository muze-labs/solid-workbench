# Native provider choice and existing task presentation

Use [the agreed plan](../provider-preferences-plan.md), including its source
inspection and gap checkpoint. Reuse PreferenceState, native StateGraph and
Metro document operations, current capability presenter and private broker.

Provider binding uses cap:registry, rdfs:member, cap:provides, cap:application
and schema:url. Co-locate registry with linked preferences. Store application
identity and launch URL together as one conflict unit, with native local
confirmed/pending/baseline terms. Never overwrite shared app metadata: use a
binding-local schema:url for launch configuration, leaving cap:application as
application identity. This scopes launch configuration to the chosen binding
and preserves independent descriptions of the same app.

Reject multiple/structured interpreted terms and externally located registries.
Preserve unrelated triples and descriptions, including other capabilities.
Reset removes only the browse membership/binding's interpreted terms.

Known installed apps mean saved shortcuts in the current Launcher with explicit
manifest or live capability declarations, plus built-in Files. Preferences
reuse its native controls and list/details. All selection policy stays editable.

Early native-binding pilot measures full readable Workbench cost before UI
expansion. Replan if existing caps cannot hold. Existing cultures apply as
recorded in the plan; no new external dependency or library infrastructure.

The maintainer says “I'll allow the extra 33 bytes :)”. Readable Workbench may

authorizes continuation of CYC118, not a general budget waiver or acceptance.


## Final composition and evaluation boundary

Optional saved-app metadata inspection belongs to the Preferences feature and
uses existing Metro/document and OLDM APIs; it is not loaded into the Launcher
home as a registry editor. SimplyFlow's model owns the capable-app projection;
the native registry remains authoritative. Unknown manifest support does not
remove the saved choice. The fixed Profile/Preferences task providers and
ordinary per-instance browse grants retain their roles.

A feature-local component layer rule wraps the displayed current provider URI.
This follows the accepted styling interface without DS token reads or another
layout component. The current native controls/section navigation are reused.
Automated phone keyboard, AX, text scaling, recovery and protocol fixtures
provide bounded evidence; manual AT, live providers and human acceptance are
separate from those checks.
