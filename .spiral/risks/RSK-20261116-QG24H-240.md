# Capability payload graph identity and format suitability

Disposition: deferred investigation for a future cycle. Potential interoperability
and data-preservation risk, not a demonstrated failure in the current supported
workflows or authorization to switch formats in CYC235. Owner: capability
protocol/participation maintainers, with domain contracts remaining app-owned.

On 2026-11-16, during CYC235 review, the maintainer asks whether JSON's tree
structure is sufficient for capability exchange, then instructs:

> Mark this as a potential risk for a future cycle to explore and perhaps switch formats.

The maintainer subsequently accepts the cycle and requests commit, merge and
push with that follow-up retained. Format selection remains open.

Current evidence: MessagePort structured cloning itself can preserve shared
references and cycles. Our serializable helper deliberately normalizes supported
plain values through JSON text: repeated objects become independent copies and
cycles are rejected by the depth/serialization rules. Raw PortConnection is not
universally restricted to that helper's value profile. Distinguish transport
capability, normalization policy and individual capability payload contracts.
Identifier references such as @id and native Turtle restoration envelopes can
represent graph relationships without cyclic JavaScript objects. These existing
mechanisms do not prove all future graph-oriented capabilities will fit safely.

Risk: a future capability may expand resources into nested objects and silently
lose shared identity, duplicate nodes or refuse cycles; different providers may
infer different semantics. Repeated objects need not denote the same RDF node,
and object identity alone must not replace stable resource/blank-node identity.
We have not reproduced graph-data loss in a current supported app workflow.

A future cycle should inventory actual request/result/restoration paths and
normalization boundaries, then probe shared nodes, cycles, identifiers, unknown
terms, multiple values, literals and cross-provider round trips. Compare current
identifier-based object payloads with explicit RDF payloads (for example Turtle
or a specified JSON-LD graph form), or other justified graph-preserving formats.
Assess reference resolution and document bases, independent implementation cost,
validation, wire/schema/version negotiation, compatibility, download/runtime cost,
cancellation/recovery and preservation of current domain semantics. Do not choose
a representation merely because its syntax permits graphs.

Decision gate: retain or explicitly change the format only after concrete
consumer evidence and maintainer confirmation. Specify which envelopes/payloads
change and how independent providers interoperate; preserving native RDF and
not putting JSON inside Turtle remain standing rules. No new protocol version,
format conversion, migration, package publication or next-cycle selection is
implemented or authorized by this risk record.
