# Preferences cycle decisions

Source: retained maintainer conversation, 2026-11-08. Explicit provenance.

The maintainer proposes Preferences UI as the next cycle and a separate app,
like Profile, potentially reducing Launcher JavaScript. They confirm the boundary
of a dedicated app normally presented in a dialog. Desired appearance resembles
Ubuntu Preferences: sections on the left and the selected section on the right;
the current app can add its own sections.

They require the existing default list-details view and prefer extending it to
creating another CSS component. After asking whether questions remain before
beginning the cycle, they answer the two outstanding questions:

- “Apply each change immediately, like Ubuntu”. This supersedes the proposed
  per-section Apply button and the old general Save behavior.
- “Edit any workspace selected inside Preferences (recommended)”. The question
  explicitly states this does not switch active workspace or close its apps.

Previously confirmed: design/discussion is part of the cycle before product
implementation; common items remain first and stable in every app; workspace
selection is separate from WebID selection. Common preferences remain shared;
workspace-specific settings remain scoped to that workspace. Do not reinterpret
immediate changes as permission to discard edits offline, overwrite remote
conflicts or execute destructive operations while a field is being typed.

The technical design below is an agent proposal for review, not an additional
human approval. JavaScript savings are a hypothesis to measure. No commit,
integration, publication or edits to other repositories are requested.

## Keyboard review request, 2026-11-08

The maintainer requests Up/Down behavior like the dropdown, Enter to switch
sections and Tab into section controls. Inspection finds ordinary buttons with
no arrow navigation; activation currently moves focus to the heading. Extend
the existing list-details component with an opt-in section shortcut scope.
Arrows move focus and wrap without selecting; native Enter selects while
keeping keyboard focus in the list, and Tab moves to the displayed section's
first enabled visible control. Shift-Tab returns to the selected section.
Pointer activation retains heading focus and phone detail navigation. Native
arrows within input/select controls are unaffected. SimplyFlow binds a single
roving Tab stop, and stable row objects retain focused DOM nodes on activation.
No new CSS component or persistence change. This is an authorized correction
inside Active CYC106; human acceptance and commit/integration remain pending.


## Icon alignment and reported stale server, 2026-11-08

The maintainer explicitly adds workspace-menu icon alignment to this cycle and
reports arrows unavailable, suspecting stale server assets. Installed the-ds
sets ds-icon vertical-align to bottom; CSS center is invalid. Apply middle to
the suite's shared svg.ds-icon default in its existing foundation style, without
editing node_modules or the external design-system repository.

Live HTTP checks on port 4174 confirm the actual process serves this checkout's
current bytes with Cache-Control: no-store. A fresh Chrome probe against that
server reproduces outer Close-button focus and child BODY focus; Down works only
after manually focusing the section. The cause is presentation focus, not stale
served bytes. Preferences now receives an initial focus request after SimplyFlow
has removed iframe inert/hidden/busy attributes. A native MutationObserver waits
for that concrete browser state; it does not render content. An immediate check
also handles an already-interactive frame. The callback targets current actions
and respects an interaction already started by the user.

Only Preferences requests this focus policy. ManagedApp validates the parent
window, origin, live task/peer and exact ticket ID/key before invoking its optional
onFocus callback. Other capability providers retain their own focus behavior.
Observer cleanup and existing private capability lifecycle remain intact. A live
server probe verifies initial focus in the iframe's selected button and the
first Down reaching Language without setup focus. Human acceptance, commits and
integration remain pending.
