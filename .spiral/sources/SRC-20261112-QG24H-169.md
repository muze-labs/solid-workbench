# Authorized second cycle

The maintainer explicitly authorizes both proposed cycles: icons, followed by
shared embedded views with Files as the first consumer. Preserve the full design
proposal at design/solid-workbench-embedded-app-views-design.md from main
63b0976df7faf5b2f729a7d2c4ae0e0523aab499. User priorities document remains preserved
in the original worktree; it does not replace this explicit cycle commitment.
Read existing broker, ManagedApp, capability dialog, Files lifecycle/navigation,
provider preferences, moldability and browser styling guidance before edits.


Maintainer review correction, 2026-11-12: plain text works, but the embedded
viewer repeats the host's “WebID / connection” control. The maintainer requires
embedded viewers to expose only view-specific UI. Inspection confirms the shared
shell enables that task control for every task, including persistent views.
Continue Active CYC168 on its verified branch: opt the viewer into content-only
embedded presentation using SimplyFlow bindings and the existing header component.
Standalone account controls remain useful; resource errors and request-specific
recovery must stay visible. No broker/authentication protocol change or new
cycle approval is needed for this correction within the authorized Files proof.


Maintainer MIME review, 2026-11-12: all `text/*` resources must be viewable as
text, including HTML source. The current exact `text/plain` check leaves this
gap; extend it to the text media family with case-insensitive type matching and
parameter handling. Keep escaped SimplyFlow text rendering, the existing Metro
read path, loaded-content preservation and the same phone/keyboard interaction.
No new app, dependency, network request or offline cache is introduced.

When additional viewers arrive, prefer a matching specific MIME viewer (for
example `text/html`) over the generic `text/*` fallback during default selection.
Preserve deliberate user selection. View-selection tabs are a possible future
UI, not part of this correction; multi-provider discovery/ranking still needs
its own implementation. RFC 9110 sections 8.3.1 and 12.5.1 were checked for
case-insensitive media types, parameters and Accept media ranges:
https://www.rfc-editor.org/rfc/rfc9110.html#section-8.3.1
https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.1
The future app preference is product policy, not a claim that HTTP specifies
capability-provider ranking. UTF-8 decoding remains the existing response.text
behavior; this correction does not introduce charset negotiation.
