# Confirmed Notebook scope

The maintainer agrees to the proposed Notebook cycle, confirms “Yes, one notebook
with rich-text blocks”, pauses to clarify “I do want to be able to load and save
different notebook documents”, then says “continue”. One open notebook at a time
supports New/Open/Save/Save As; each contains ordered blocks. This is explicit
implementation authority for the evidenced missing Workbench integration, not
human acceptance or authority to commit, merge or publish.


After the explicit prototype/gap checkpoint, the maintainer confirms the ordered
rich-text-block workflow. On pausing, they clarify that different notebook
documents must load and save. The assistant confirms one open document at a time
with New/Open/Save/Save As and preserved local copies; the maintainer resumes
with “continue”. This correction supersedes any single-document-only assumption.


The maintainer rejects the incomplete interaction integration and confirms
“Yes, complete those interactions” after the concrete probe/checkpoint: cursor
movement in all directions, cross-note selection/formatting/copy/paste and
boundary split/join; Enter creates/splits notes, Shift+Enter inserts a line break.
Preserve the implemented multiple-document/native recovery layer. No acceptance.

preferences: Invalid app or owner context." Investigation finds a fixed app

They explicitly permit recording this on the roadmap instead of fixing it now.
Retain both requirements as deferred work; this does not authorize or claim a
generic Preferences refactor in CYC199 or accept the current Notebook cycle.


The maintainer requests a Notebook UI correction using Files and Presenter as
precedents: visible New/Save/Save As toolbar operations; the notebook title as
the app heading and HTML/tab title; an edit button for renaming; no visible block

explicit correction within the existing Active Notebook cycle. Existing markup
shows the gap: a permanent title form, document commands inside a disclosure,
numbered list markers and a border around every editor. No acceptance/delivery.


The maintainer further specifies the header toolbar beside the title, as in
Files; removes every disclosure/collapse surface and all split/join/selection
buttons; requests a Ctrl+K link dialog; and chooses Shift+arrow/native mobile
selection, Enter splitting and Delete/Backspace joining. This supersedes the
intermediate visible-in-content toolbar and remaining disclosures. Retain the
agreed multi-document workflow through labelled native Open/Save As dialogs.

The maintainer reports that Bold/Italic and other formatting flash the whole app.
A disposable native Chrome probe confirms selected-text Bold destroys all three

controller formatting through the structural Project/Run path, even though the
published controller already edits the affected adapters in place and emits
ordinary change events. Correct this local regression in the previously confirmed
formatting workflow, retaining formatting semantics, focus, native RDF/autosave
and composition/operation guards. No new editing mode or persistence policy.


After reviewing the H1, narrow header and in-place formatting corrections, the
maintainer explicitly says “accepted, commit, merge and push please”. This accepts

into current main after exact integration validation, and pushing main/the cycle

exist; no historical approvals are invented. The earlier supplied collection
