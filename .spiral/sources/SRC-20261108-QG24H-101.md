# Workspace product discussion and implementation scope

Source: maintainer conversation, 2026-11-08, retained summary of explicit intent.
Desktop/phone start screen; manifest icons with user overrides; editable workspace
titles, default Solid Workbench; profile storage Files shortcuts; multiple contexts
under one selected WebID. Shared preferences stay shared; app preferences may be
workspace-specific. Switch closes current apps and restores selected apps.
Create/delete in Workbench Preferences; dropdown entries only switch. Protect
default and active workspaces. External deletion of default triggers initial
setup after confirmed absence; deletion retains linked data. Reuse default
address book, create only if none; fuller Contacts behavior is separate scope.

The maintainer says: “If that completes our design, lets start the cycle to
implement it.” Asked to distinguish foundation from Contacts work, they select:
“Workspace/Launcher foundation first; Contacts enhancements next”. Widgets and
app store remain later. These instructions authorize implementation/evaluation,
not commits/integration/publication. Pending planning documents retain detailed
conversation decisions, proposals and earlier superseded recommendations.


During implementation the readable Workbench graph measured 205233 gzip bytes.
Presented with a diagnostic-app split or narrower scope, the maintainer instead
says: “allow the budget to expand for now, we'll revisit later.” This explicitly
authorizes a temporary budget exception for the current work; retain measurements
and follow-up. It does not select a diagnostic app or reduced feature scope.

## Workspace switch focus review, 2026-11-08

The maintainer reports that switching correctly restores the new workspace's
apps but activates the last restored app; the current Launcher tab should remain
focused. Broker.restore opens each window using the normal explicit app-opening
path; the Launcher subsequently focuses only a DOM heading, which does not
select its browser tab. Keep this correction scoped to automatic restoration on
workspace switching; ordinary shortcut launches still activate the selected app.
This is further review within Active CYC100, not acceptance or commit permission.

Chrome reproduction shows that the Launcher cannot reliably retain tab focus
when opening restored tabs: opening consumes transient activation, which Chrome
requires for subsequent page activation. The maintainer is presented with keeping
tabs/browser-controlled focus versus restoring as separate app windows and
selects “Keep tabs and accept browser-controlled focus”. This supersedes the
focus-preservation requirement for tab mode. Keep normal tab restoration and
remove ineffective focus workarounds; no change to launch preferences is selected.
