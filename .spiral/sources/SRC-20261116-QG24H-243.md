# Independent Preferences cycle confirmation

On 2026-11-16 the maintainer questions a proposed shared selection toolbar:
“I worry that trying to tie these together might end up conflating different
usecases and not actually simplify anything”. After the proposal is withdrawn,
they say “Agreed, lets find another cycle”. No toolbar extraction is selected.

The assistant proposes Preferences for independent apps, with the concrete goal
that an independent app can open common preferences and supply its own settings
section without rebuilding Preferences. It reports the fixed caller list and
direct suite settings imports, and proposes existing/independent consumers,
native settings/draft/conflict preservation, optional unavailable contributions,
phone/keyboard verification and download measurement. It explicitly identifies
where contributed UI executes as a design question to settle before implementing
a loading mechanism. The maintainer answers “yes”.

Interpretation: goal and evidenced gap are confirmed. The confirmation does not
select in-process JavaScript versus an app-hosted embedded view. A subsequent
question presents these alternatives, recommending the app-hosted view; its
answer is pending. No acceptance, commit, integration or publication is inferred.


## Execution boundary confirmed

The maintainer selects “App-hosted embedded settings view (recommended)”.
Proceed with app-owned documents and draft/save/recovery lifecycles; Preferences
owns common settings and navigation. No in-process third-party code loading.
The existing local WorkspaceBroker (already used for standalone app tasks) can
own the section's scoped port directly inside Preferences. This avoids granting
general nested embed authority in the outer workspace broker. The outer broker
continues to guard Preferences closure; Preferences must prepare its owned view
and retain failed/unready drafts until retry or explicit discard. Section URLs
must be verified against the actual caller origin supplied by the broker, not
an input origin assertion. Existing configured-provider URL checks stay intact.


## Account chrome review correction

The maintainer explains that embedded apps use containing-app connection controls,
while separate windows already have an account dropdown, then says “please do”
to removing the redundant task connection button. This is authorized review
correction within Active CYC242. The shared shell must use actual embedding,
not task identity, for account-menu and embedded-layout visibility. Remove the
standalone button. Preserve draft recovery when leaving Preferences to use the
containing app's Account controls, and verify the window-task dropdown. No new
cycle acceptance, commit, merge or publication is inferred.


## Empty embedded header correction

The maintainer observes the space left after removing the account button and
confirms “agreed, lets fix that”. The existing embedded minimum height and
header padding still allocate an empty strip. Within Active CYC242, remove those
embedded-only dimensions while retaining normal layout for visible toolbar
buttons/status and keeping the header rendered for its recovery dialog. The
page-layer rule must also override compact-header sizing. Remove the obsolete
recovery-specific header display:none rule so dialogs are not hidden by an
ancestor. Verify empty geometry, dynamic visible content, native recovery focus
and separate-window chrome at phone/desktop sizes. No data or download requests
change; no acceptance, commit or integration is inferred.


The maintainer steers toward content-owned spacing: “simplest idea is to let the
content of the header supply a margin, and not put any on the header itself”.
Apply this to embedded chrome: zero header margin/padding/minimum size; visible
children supply their own existing spacing and control size. Do not add an
empty-content visibility predicate or hide the header ancestor.
